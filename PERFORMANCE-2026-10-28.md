# Vector PNI — оптимизация производительности

Дата: 28.10.2026 (Europe/Moscow). Проект: drone-lab. База: `2d79f6c1e505aa6c60f8ee03dbf7d348861cc086` (Vector PNI 2.0). Изменения локальные; commit/push/deploy не выполнялись.

## Вывод и выбранная архитектура

Оставлены React + Three.js + JavaScript. Главный измеренный расход — CPU-подача большого числа объектов/материалов в WebGL, а не расчёт анимации. Подтверждённое улучшение получено через InstancedMesh, повторное использование идентичной геометрии и материалов, кеширование примитивов и устранение явных временных объектов в RAF. Модель, материалы, число треугольников, освещение, DPR, интерфейс и данные компонентов сохранены.

WASM и .NET runtime в production не добавлены. Подготовлен отдельный C++-исходник и harness для будущего пакетного сравнения математического ядра, но компиляция/измерение C++ не выполнялись: доступного Emscripten не обнаружено. C# / Blazor не прототипирован: измерения не выявили вычислительного участка, который оправдывает отдельный runtime. Нативный .NET benchmark нельзя выдавать за WebAssembly, поэтому такой подмены сравнения нет.

## Методика

- Сначала заморожена исходная production-сборка в `C:\Sites\MyWebsite\vector-performance-baseline`, доступная через Vite preview на 5176. Оптимизированная сборка — тот же Vite preview на 5175.
- Headless Chrome 156, Windows, Intel UHD / ANGLE D3D11, viewport 1440×1000, DPR 1. Шейдеры могли использовать кеш GPU; это не серия запусков после перезагрузки машины.
- Для каждой версии/CPU-настройки — 3 прогона одинакового сценария: загрузка → готовая модель → GC → автовращение 4 с → разборка 2 с → сброс → 80 hover-событий.
- HTTP-кеш отключён через CDP. Не добавляются HTTP-заголовки, мешающие внешним шрифтам. Канал сети не ограничивался; локальный Vite preview отдаёт JS без production-сжатия. Размер gzip измерен Vite отдельно. Поэтому время ready — локальная метрика появления модели, а не обещание загрузки через мобильный интернет.
- Каждый контрольный прогон выполняется в новом browser context, без накопления диагностических обёрток между измерениями. Итоговые таблицы FPS не используют HeapProfiler allocation sampling.
- Отдельно выполнены прогоны со сбором аллокаций, GPU timer queries и учётом живых bufferData-буферов. Эти диагностические инструменты не импортируются production-приложением.
- В таблицах ниже — медианы 3 прогонов. Chrome CPU throttling 4× — искусственное замедление, не реальный телефон/ARM-процессор.
- Старые предварительные прогоны, где могли накопиться измерительные обёртки, исключены из контрольной таблицы. Показания FPS под allocation profiler также не используются как обычный FPS.

## GPU и память

- `EXT_disjoint_timer_query_webgl2` доступен. Отдельная серия вращения: GPU median 1.371 → 1.327 мс, p95 1.402 → 1.353 мс, по 72 валидных образца без disjoint. Это время GPU-команд, не процент GPU utilization и не измерение энергопотребления.
- Сумма живых WebGL bufferData-выделений: 19 898 684 → 2 994 492 байт. Число живых buffers: 4117 → 704. Текстуры, render targets, драйверные накладные расходы и вся VRAM в эти значения не входят.
- Семплированные аллокации при вращении: медиана около 525 → 65.5 кБ на отрисованный кадр. Параметры: CDP HeapProfiler, samplingInterval 32768, включая объекты, собранные minor/major GC. Это оценка байтов по выборке, не точное число JS-объектов. Сырые данные находятся в `bench/results/*-allocations.json`.
- Из RAF вынесены Object.entries(groups), массивы пар и нулевых offsets, массив camera keys и создававшийся каждый кадр THREE.Spherical. Точное общее число создаваемых объектов браузер/renderer не подсчитывалось; вымышленных значений «объектов/кадр» нет.
- В покое не вводится постоянный RAF, в скрытой вкладке отрисовка остаётся остановленной. Энергопотребление в ваттах, температура и батарея не измерялись; уменьшение работы CPU не выдаётся за измерение батареи.

## Изменения реализации

### Повторное использование и InstancedMesh

- Одинаковые RoundedBox/Cylinder/rod-примитивы создаются через локальный кеш; их размеры и сегментация не изменены.
- `viewer-instancing.js` сравнивает layout и фактические байты position/normal/UV/index; коллизии hash дополнительно проверяются побайтно. Данные разных воздушных профилей не подменяются «похожими» примитивами.
- Материалы сравниваются по настройкам, включая цвет, roughness/metalness, текстуры и прочие enumerable-поля. Разные texture UUID остаются разными.
- Инстансинг применяется только внутри одного компонента при одинаковой геометрии/материале. Прозрачные, отрицательно масштабированные и custom-shader объекты не объединяются.
- Исходные локальные матрицы копируются в instanceMatrix. Матрицы статических mesh перестают пересчитываться через matrixAutoUpdate каждый кадр; движение остаётся на прежних группах частей.
- Проверены и сохранены part ID для raycasting, разборка, выделение, все ракурсы и сброс. Bounding box/sphere инстансов рассчитаны; frustum culling не отключён.
- Оригинальные mesh для отдельных preview сохраняются через WeakMap, а не через циклический userData. Preview продолжает выбирать один мотор/винт/ESC по прежним координатам.
- Для выделения переиспользуется набор уникальных материалов части. При cleanup освобождаются также instanceMatrix-ресурсы, оригинальные preview-геометрии/материалы и общие текстуры без повторного уничтожения одной ссылки.

### Исправление восстановления WebGL

Новый тест сравнения снимков выявил потемнение модели после restore: GPU-only PMREM render target терял содержимое. Теперь после восстановления контекста окружение генерируется повторно теми же RoomEnvironment/параметрами; предыдущий render target утилизируется. В Chrome и Firefox снимки до потери и после восстановления совпадают побайтно. Ошибка генерации окружения оставляет понятное сообщение, а описания компонентов доступны.

## C++ / C# / WebAssembly

| Вариант | Что фактически выполнено | Результат |
| --- | --- | --- |
| A: JS/React/Three до | Полное профилирование production snapshot | Таблицы выше |
| A: оптимизированный JS/Three | Реализация, измерения и регрессия | Выбран для production |
| B: C++ / Emscripten WASM | Подготовлены `bench/spring-kernel.cpp`, команда сборки и browser harness с проверкой parity и одним пакетным вызовом на кадр | Не компилировался и не измерялся: Emscripten недоступен |
| C: C# / .NET WASM | Проверен установленный SDK 10.0.401; wasm workloads отсутствуют. Рассмотрена целесообразность | Не реализован: нет обоснованного вычислительного ядра; React/Three сохранены |

JS microbenchmark в браузере использует настоящий springTo, 23 состояния (assembly + 16 highlights + 6 camera axes), переменный dt, меняющиеся цели, прогрев и проверочные checksum. 5 серий × 200 000 кадров: медиана 47.3 мс, то есть около **0.237 микросекунды на кадр для всего пакета**. Это синтетический тест математики, не FPS приложения. В реальной сцене большинство состояний часто уже в покое.

Даже устранение всей этой математики не устранит стоимость подачи сотен draw calls. Поэтому добавление загрузки WASM, межъязыкового API или .NET runtime сейчас не обосновано измерениями. Это не утверждение, что C++/C# вообще медленнее JS. Полного выполненного A/B/C сравнения приложения нет; отсутствующие результаты B/C намеренно отмечены как отсутствующие.

Прототип B не импортируется приложением и не попадает в production bundle. После установки Emscripten можно выполнить команду из `bench/README.md` и вызвать `runVectorMathBenchmark({wasm:true})` на отдельной странице `/bench/math.html`. Harness переиспользует linear memory, проверяет совпадение значений/скоростей и учитывает setup time. Сборка прототипа в этой среде не проверена.

Документация для выбора архитектуры: [Three.js InstancedMesh](https://threejs.org/docs/pages/InstancedMesh), [Emscripten: избегать лишних WebGL-вызовов](https://github.com/emscripten-core/emscripten/blob/main/site/source/docs/optimizing/Optimizing-WebGL.rst), [Emscripten optimization](https://emscripten.org/docs/optimizing/Optimizing-Code.html), [Microsoft: Blazor download size](https://learn.microsoft.com/en-us/aspnet/core/blazor/performance/app-download-size?view=aspnetcore-10.0).

Размер JS вырос примерно на 1.2 кБ gzip из-за кода оптимизации и полного восстановления окружения. Загрузка модели ускорилась за счёт меньшего количества CPU-работы и повторного построения примитивов, а не за счёт уменьшения числа полигонов или подмены модели.

Three.js и React нужны на первом экране. Разбиение этих обязательных модулей на файлы само по себе не уменьшит загрузку, а отложенный viewer отложит интерактивность. Дополнительный code splitting/lazy loading без подтверждённого узкого места не вводился. Настройки сжатия/кеша внешнего GitHub Pages не менялись и сервер не добавлялся. Существующий hashed asset pipeline сохранён.

`npm.cmd run build`, `npm.cmd run build:pages`, `npm.cmd run test:motion`, `npm.cmd run test:geometry` успешно выполнены. Base `/`, статический `pages-dist`, workflow и зависимости не изменены. Vite предупреждает о chunk >500 кБ без сжатия; предупреждение не скрыто изменением порога. Bench/исходники C++/результаты профиля не включаются Vite в production output.

## Оставшиеся ограничения

Нет измерений на реальных iPhone/Android, Safari/WebKit, слабых физических GPU, батареи/температуры, многочасового heap-профиля и фактических сетевых условий посетителей. Нет точного подсчёта всех объектов/кадр или аппаратного GPU utilization %. JS heap, GPU buffers и allocation sampling — разные ограниченные измерения, не сумма всей RAM/VRAM. B/C не измерены и не встроены. На GPU-bound устройствах выигрыш может отличаться. Внешний опубликованный сайт остаётся прежним до отдельного разрешения на публикацию.

### Примечание о dev-среде

Во время перезаписи тестового файла Windows watcher dev-сервера Vite завершился с EBUSY. После отдельного повторного запуска финальная benchmark-страница и её преобразованный JS-модуль возвращают HTTP 200; runVectorMathBenchmark присутствует. Это ограничение локального watcher при редактировании файлов, не ошибка production viewer. Сборки и независимые production-preview проверки выполнены успешно. Первоначальная ошибка разрешения отсутствующего optional WASM-модуля в dev-harness исправлена динамическим импортом; обычный JS benchmark не пытается его загружать.
